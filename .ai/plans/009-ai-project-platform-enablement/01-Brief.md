# Brief 009 — Платформа для AI Project v2: перенос идей брифа 011

Дата: 2026-08-21

## 1. Назначение

Бриф 011 (ai-project: .ai/plans/011-ai-project-v2/01-Brief.md) содержит принципы P1–P12,
которые должны применяться во всех greenfield AI-проектах. Часть этих принципов относится
не к ОС, а к **платформе** — её контрактам, шаблонам, практикам и модели контекст/нода.
Этот бриф фиксирует, какие идеи портируются на платформу, в каком виде и до какого момента
(«пока проекты не запущены — последний шанс»).

## 2. Источник и зафиксированные решения

Источники: бриф 011; беклог .ai/backlog/multi-node-hermes-split.md; обсуждение с владельцем
платформы (сессия 2026-08-21). Решения владельца (не переигрываются):

| # | Вопрос | Решение |
|---|---|---|
| R1 | Структура артефактов | Один план 009, задания секциями T1–T9 |
| R2 | Форма расширяемости ai-platform.yaml | Гибрид: закрытое ядро + зона расширений |
| R3 | Multi-node сейчас | НЕ создавать группы ролей (hermes/db/projects в беклоге — примеры). Модель: размещение ПО МОДУЛЯМ — какой модуль на какой сервер контекста; модуль может быть «для всех серверов» (шаримый) |

## 3. Задания

### T1 — Шаблонное дерево слоёв + переименования + type: typescript

**Суть (P12, §6, §7 брифа 011).** Шаблоны платформы образуют дерево наследования:
template-python ← template-landing ← template-landing-realty; template-react; template-ai-os
(корневые — без parent; template-context вне дерева). `make new-project` конкатенирует
цепочку родитель → … → выбранный слой в папку проекта (рендер {{PLACEHOLDERS}} — существующим
механизмом). Переименования backend→python, frontend→react с deprecated-алиасами; в
ai-platform.yaml#type добавляется `typescript` (CI-ветвление deploy-project.yml уже
принимает имена: typescript|react|frontend, python|backend — осталось расширить schema enum).

**Что даёт.** template-ai-os/template-landing(-realty) как цепочки слоёв; каждый слой добавляет
ровно одну техническую цепочку; новые шаблоны не копипастят базовые файлы.

**Труд.** M. Точки: core/internal/scaffold/project_scaffolder.py (resolving + overlay),
гейт templates-check (циклы, перезапись файлов, requires_practices_version по всей цепочке),
core/templates/template-manifest.yaml, template.yaml (поля parent:, overrides:),
templates/AGENTS.md — каноническая карта наследования, алиасы в CI-ветвлении и schema.

**Границы.** Слой — статичное дерево файлов + {{PLACEHOLDERS}}; init/postinstall-генераторы
запрещены; никакого дизайна/текстов/домена. Молчаливая перезапись файла родителя — ошибка;
осознанная — только через overrides: дочернего слоя.

**Пограничные случаи.** Цикл parent — ошибка валидации; неизвестный parent — ошибка;
конфликт дочерний/родительский без overrides: — ошибка; template-context не участвует в
цепочках; старые проекты не мигрируют (шаблон применяется только при new-project).

**Критерии готовности.** templates-check гоняет цепочки (циклы/overrides/requires по цепочке);
scaffold конкатенирует цепочку с перезаписью только по overrides:; оба имени (backend|python,
frontend|react) принимаются везде; type: typescript проходит schema и CI-ветвление.

### T2 — Конвенция «папка = элемент» как практика платформы

**Суть (P3, §8).** Проект AI Project v2 — это папки capabilities/entrypoints/roles/plugins,
файлы подхватываются автоматически (имя файла = id), состав проекта виден по папкам, god-config
отсутствует. Сам рантайм авто-подхвата — ОС (не платформа). Платформенная часть: практика
**layout-convention** (canon practices_manifest.yaml, L3, languages: typescript, channels
local/ci/verify) — статическая валидация конвенции папок/имён; и template-ai-os как носитель
структуры (через T1).

**Что даёт.** Нарушение конвенции ломает гейт (а не ревью); новый файл по конвенции — виден
системе без правки конфигов.

**Труд.** S–M. Новый check в каноне практик + генераторы/executor; шаблонная часть — с
template-ai-os.

**Границы.** Платформа валидирует СТРУКТУРУ (папки, имена = id, запрет god-config-файла
состава); рантайм-подхват и zod-схемы — ОС. Обычные python/frontend-проекты практикой не
проверяются (ветвление по type).

**Пограничные случаи.** Проект без папки plugins/ (пустые папки в git); проект с дополнительными
папками — допустимо или ошибка? (в сессию); adopted-проекты — вне конвенции.

**Критерии готовности.** Новая практика в каноне; project-check/CI/verify её исполняют;
template-ai-os-проект проходит, нарушение — понятная ошибка со списком путей.

### T3 — Гибридная расширяемость ai-platform.yaml + deprecation N-2

**Суть (P5, P6, R14, §4, §13; решение R2).** Манифест проекта получает:
(1) **закрытое ядро** — деплой/L1-поля (name, type, target_node, needs.domain, сети, секреты)
остаются в центральной схеме и расширяются только версией;
(2) **зону расширений** — needs/доп. секции добавляются процедурой расширения (реестр
потребителей, валидация секции её владельцем) без правки центральной схемы и без миграций
форматов;
(3) **версию манифеста** как носитель deprecation-политики N-2 + CHANGELOG контрактов.
Старые ai-platform.yaml читаются всегда (backward-compat).

**Что даёт.** Добавление новой потребности проекта (новый needs-сервис, секция capability)
не требует правки платформенной схемы и не трогает существующие проекты; изменения контракта —
предсказуемы (deprecation, а не поломка).

**Труд.** M. Схема (core/schemas/ai-platform.schema.json), валидатор, процедура расширения в
AGENTS.md, гейт на версию/депрекейшн.

**Границы.** L1-поля НИКОГДА не попадают в открытую зону; неизвестные поля в открытой зоне —
поведение решает сессия (ошибка vs warning, см. §8 Q2); расширение — через процедуру, а не
молчаливую правку схемы.

**Пограничные случаи.** Старый манифест без version — читается как версия 1; поле переехало из
ядра в зону расширений — запрещено (ядро только растёт по процедуре); конфликт имён секций
двух потребителей — ошибка регистрации.

**Критерии готовности.** Схема v2 с закрытым ядром и зоной; процедура расширения описана и
гейтится; манифесты существующих проектов валидны без правок; deprecation-политика N-2
зафиксирована в AGENTS.md.

### T4 — Практики TS/cordis: vitest, strict-конвенции, статические гейты ОС

**Суть (§6.4; решение R6).** В канон практик добавляются:
- **vitest** — прогон тестов TS-проектов (baseline, L3, languages: typescript/react, channels
  local/ci/verify) — сейчас для TS есть build/eslint, прогона тестов нет (проверено по
  practices_manifest.yaml);
- **tsconfig-strict** — конвенция флагов (strict, noUncheckedIndexedAccess,
  exactOptionalPropertyTypes) — шаблоны несут tsconfig, канон исполняет;
- подмножество статических гейтов ОС (only-sdk-imports, no-deep-imports, no-raw-vendor-clients,
  glossary-drift, capability-manifest-valid, role-grants-valid, generated-drift,
  no-domain-in-kernel, no-user-strings-in-os) — поставляются пакетом @ai-project/static и
  исполняются каноном как agent-check-аналог для TS (канал local).

**Что даёт.** Новый AI-проект получает проверки «из коробки»; нарушение ломает гейт.

**Труд.** S–M. Новые check-записи в каноне + executor (npm run test / npx-гейты); конфиги
strict — в шаблонах (T1).

**Границы.** Платформа исполняет, но НЕ владеет содержимым гейтов ОС (их поставляет пакет);
для не-ОС проектов — только vitest/tsconfig-strict.

**Пограничные случаи.** Проект без тестов (vitest skip-политика); пакет @ai-project/static ещё
не опубликован — гейты включаются флагом/версией (нет пакета — нет гейтов, не ошибка);
конфликт версий пакета и канона.

**Критерии готовности.** Новые checks в practices_manifest.yaml; project-check/CI исполняют;
template-ai-os-проект зелёный; нарушение — блок гейта с понятным выводом.

### T5 — GHCR npm для @ai-project/*

**Суть (§7; решение R7).** Код ОС доставляется только пакетами npm из GHCR — никакого checkout
репозитория ОС в контексты. Платформенная ops-разблокировка: npm-реестры контекстных org
(ghcr.io/npm), токены (публикация — CI-секрет; pull на ноде/в CI проектов — по аналогии с
GHCR_PULL_TOKEN образов), шаблон publish-workflow (semver, pin точных версий проектами,
provenance/SBOM по DevOps-политике платформы). Scope: **@ai-project/***.

**Что даёт.** W1/W2 брифа 011 не блокируются инфраструктурой; версионированная доставка пакетов.

**Труд.** S–M. Org-реестры, provision токенов, workflow-шаблон, docs.

**Границы.** Платформа даёт реестр/токены/процедуру, но не владеет содержимым пакетов;
пакеты публикует CI монорепо ОС.

**Пограничные случаи.** Анонимный pull (реестры приватные — только токеном); несколько org
(контекстов) — токены per-org; rotation токенов — по канону ротации ключей.

**Критерии готовности.** npm-пакет публикуется в GHCR org и ставится проектом-консьюмером
без checkout; токены зарегистрированы в secret-definitions.yaml.

### T6 — Multi-node контракт: 1 нода = 1 контекст, размещение по модулям

**Суть (решение R3 + беклог).** Фиксируем контрактное направление:
- **1 нода = 1 контекст** — жёстко: contexts[] в node.yaml → единственная запись
  (контекст может занимать несколько нод, но нода принадлежит ровно одному контексту);
- **1 контекст = N нод** — без фиксированных групп ролей: каждый модуль либо приписан к
  конкретной ноде контекста, либо объявлен «для всех серверов» (шаримый: общие БД/кэш/LLM/
  хранилище/мониторинг);
- **контекстный слой конфига** — одно место, где описаны ноды контекста, приписка модулей к
  нодам и адреса шаримых модулей; enabled-modules каждой ноды выводятся из этого слоя;
- «всё на одной ноде» (как сейчас) остаётся каноном — надстройка не ломает существующее.

**Сейчас:** только контракт (структура конфига, валидация, вывод ноды, миграция существующих
node.yaml). **Пост-релиз** (беклог, с актуализацией «группы ролей → размещение по модулям»):
фактический шаринг между нодами, сети/доступы, порядок старта (данные раньше потребителей),
единый мониторинг всех нод.

**Что даёт.** Позже не придётся мигрировать конфиги/проекты при выносе hermes или БД на
отдельный сервер; направление зафиксировано до запуска проектов.

**Труд.** Контракт S–M; реализация L (пост-релиз, вне этого задания).

**Границы.** Контракт описывает РАЗМЕЩЕНИЕ, не топологию сети (сети/DNS/доступы — пост-релиз);
шаримые модули открываются только нужным нодам (безопасность не деградирует).

**Пограничные случаи.** Миграция существующих node.yaml (все — один контекст, тривиально);
модуль, допустимый только в одном экземпляре на контекст; нода без шаримых модулей;
формат контекстного слоя (см. §8 Q3).

**Критерии готовности.** contexts[] → единственная запись (гейт); контекстный слой описан и
валидируется; enabled-modules ноды выводятся из слоя; single-node режим работает без изменений.

### T7 — Реестр проектов: единственный писатель

**Суть (P3; решение R4).** Сегодня проект описан в трёх местах (node.yaml projects[],
ai-platform.yaml, platform/projects/*.yaml) с дублями полей (type/domain/expose). Канон:
**node.yaml projects[] — операционный SoT**; ai-platform.yaml генерируется скаффолдером из SoT
(проект получает срез); platform/projects/*.yaml — только L2-оверрайды мониторинга;
drift-гейт сверяет представления (расхождение = ошибка с repair-таргетом).

**Что даёт.** Один источник правды на поле, нет коллизий при ручных правках; агент всегда
знает, где править.

**Труд.** M. Генерация/сверка + гейт + docs; трогает scaffold и (аккуратно) deploy-цепочку.

**Границы.** Писатель полей проекта — scaffold из SoT; ручные правки SoT — только осознанные,
drift-гейт ловит.

**Пограничные случаи.** adopt-project (SoT создаётся из репозитория); ручная правка
ai-platform.yaml в проекте — поведение гейта (блок vs repair, §8 Q4); конфликт доменов —
first-claimant (уже есть).

**Критерии готовности.** Один писатель на поле; drift-гейт зелёный на существующих проектах;
repair-таргет восстанавливает производные представления.

### T8 — Словарь и правила обобщения

**Суть (P7, §2.3, R4/R5).** Резервирование терминов платформы (контекст, нода, проект, шаблон,
модуль, практики, манифест) — в проектных/ОС-доках они не переопределяются; glossary-дисциплина
в проектных AGENTS.md/AI-PLATFORM.md (гейт-проверка конфликтных терминов); «правило трёх»
(перенос в платформу после третьего идентичного применения) и «правило двух ручек»
(обобщение с >2 параметрами отменяется) — в канон приёма фич платформы (root AGENTS.md).

**Что даёт.** Общий язык платформа/ОС/проекты; предсказуемый приём новых фич в платформу.

**Труд.** S. Док + опциональный гейт терминов.

**Границы.** Гейт — advisory/L3 на старте (не блокировать ложными срабатываниями).

**Пограничные случаи.** Термин «контекст» в Cordis-коде ОС (бриф 011 уже решил: ди-контейнер
ctx); расхождение словаря @ai-os/* vs @ai-project/* (§8 Q1).

**Критерии готовности.** Секция резервирования терминов в root AGENTS.md; R4/R5 в каноне;
гейт терминов работает на примере.

### T9 — Аналитика событий платформы (опционально, P9)

Добить покрытие событий деплоя/проектов в платформенные хранилища (Loki/Prometheus/
ClickHouse/Langfuse/audit). Большая часть уже есть; задание = инвентаризация событий и
дозапись недостающих. Труд S. Может быть вынесена из волн.

## 4. Не портируем (с обоснованием)

| Идея брифа | Почему нет |
|---|---|
| P8/§16 HITL-апрувы | Платформа операторская (make/CI/forced-command + аудит), не пользовательская; пользовательские апрувы — в ОС |
| P11 invoke-spine | Эквивалент уже есть: канонические глаголы + forced-command receive + DeployOrchestrator |
| P2, P10 | Уже соответствуем: бот ≠ сайт (отдельные проекты); живой прогон = requires_node E2E + release checklist |
| Дробление node.yaml на папки | Churn в SoT перед запуском ради косметики; файловая композиция окупается на проектном уровне (T1/T2) |
| §13 content-on-volume hot-reload | Конвенция тома контента — до первого контентного проекта; не контракт «навсегда» |

## 5. Severity

| Уровень | Задания |
|---|---|
| CRITICAL | T1, T3, T6 — контракты, которые каждый проект понесёт в себе |
| HIGH | T4, T5, T7 — практики и инфраструктура до первых запусков |
| MEDIUM | T2, T8 — аддитивные, но дешёвые сейчас |
| LOW | T9 — опционально |

## 6. Порядок и процесс

Предложение (уточняется на старте): Волна 1 = T3+T6+T7 (контракты); Волна 2 = T1+T5
(шаблоны/типы/npm); Волна 3 = T2+T4 (практики); Волна 4 = T8 (+T9). Каждая волна — сессия
проработки → девплан волны (как в брифе 011 §24), реализации — по утверждённому девплану.
