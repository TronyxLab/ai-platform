## DATA-101: Payload receive — мульти-файловая замена без транзакции + удаление бэкапа на error-пути
- **Severity:** HIGH · **Confidence:** HIGH
- **Files:** core/internal/deploy/receive_flow.py · **Symbols:** `ReceiveFlow.deploy` (backup:427-434, replace-loop:441-462, `finally rmtree(backup_dir)`:485-486), `DeployOrchestrator._rollback_deploy` (core/internal/deploy/orchestrator.py:593-614) · **Invariant:** payload-набор {docker-compose.yml, ai-platform.yaml, .env.platform, practices.lock} в target_dir заменяется all-or-nothing; данные для отката переживают неудачную попытку
- **Violating scenario:** START: target_dir содержит консистентный старый payload; бэкап-копии в `backup_dir` (создан ВНУТРИ target_dir, receive_flow.py:427). Операция: цикл `os.remove(dest)` → `Path(item).replace(dest)` (receive_flow.py:452-460). Сбой: OSError/SIGKILL/диск full на 2-м из 4 файлов. END: (а) смешанный набор — новый compose + старый .env.platform/practices.lock; (б) `finally: shutil.rmtree(backup_dir)` (receive_flow.py:486) УНИЧТОЖАЕТ единственную копию предыдущего payload — rollback-путь orchestrator.py:606-607 не достигнут (исключение вышло до `orchestrator.deploy`). END некорректен: деплой-набор рассинхронизирован (env нового кода против старого compose), восстановление невозможно. Дополнительно окно `os.remove`→`replace`: dest отсутствует на диске — параллельный читатель (`docker compose config` в status/monitoring) получает ENOENT.
- **Evidence:** receive_flow.py:30-32 заявляет «сбой не оставляет частично перезаписанных файлов» — гарантия per-file, не per-set; rmtree(backup_dir) в finally безусловен. · **Impact:** полусогласованный прод-payload без средств отката; следующий receive перезапишет, но до него проект в неконсистентном состоянии. · **Minimal fix:** backup_dir вынести из target_dir; на exception-пути — restore из бэкапа до rmtree; replace без предварительного remove (обработать root-owned стюб через права каталога). · **Required test:** fault-injection на 2-м replace → assert target_dir = старый набор (байт-в-байт) + backup сохранён. · **Phase:** W1

## DATA-102: G2 generate_platform_env — 3 файла одним прогоном, запись plain open("w"), без atomic_writer и без транзакции
- **Severity:** MED · **Confidence:** HIGH
- **Files:** core/internal/scripts/generate_platform_env.py:706-733 · **Symbols:** `main` (write platform-env.yaml:721-722, smoke_env_generated.py:730-731, env_defaults_generated.py далее) · **Invariant:** generated-файлы на диске всегда валидны (parse-able) и взаимно согласованы (yaml ↔ smoke ↔ helpers)
- **Violating scenario:** START: свежие файлы. Операция: `make generate-manifests` → последовательная запись тремя `open(..., "w")` без temp+rename. Сбой: прерывание (Ctrl-C/OOM/agent kill) внутри `f.write`. END: усечённый platform-env.yaml (или smoke_env_generated.py) в рабочем дереве; читатели — provisioner (`yaml_loader.load_platform_env`), conftest (import smoke_env_generated) — получают ConfigParseError/ImportError. Кросс-файловый вариант: crash между файлом 1 и 2 → новый yaml + старый smoke (дрейф, рантаймом не детектируется, ловится только CI-гейтом check-manifests). Маркера консистентности нет.
- **Evidence:** TRAP в коде (generate_platform_env.py:707-719) фиксирует seam open_fn для гейта fault-injection, но сам механизм записи не атомарен; atomic_writer в импортах отсутствует. · **Impact:** усечённый файл коммитится при обходе pre-commit; на ноде попадает через core-deliver. · **Minimal fix:** мигрировать 3 записи на atomic_write_text + порядок: сначала py-файлы, yaml последним (или общий tmp-dir + поочерёдный replace). · **Required test:** fault-open после 1-й записи → assert все 3 файла = старое содержимое. · **Phase:** W2

## DATA-103: atomic_writer fsync-политика — fsync файла есть, fsync каталога после os.replace отсутствует
- **Severity:** MED · **Confidence:** HIGH
- **Files:** core/internal/shared/atomic_writer.py:111,133 · **Symbols:** `atomic_write` · **Invariant:** «crash-safe: содержимое на диске до переименования» (atomic_writer.py:79) — в т.ч. после power loss
- **Violating scenario:** START: старый файл. Операция: write+fsync(tmp) → os.replace(tmp→target). Сбой: power loss сразу после replace. END: rename не обязан быть durабтным без fsync родительского каталога (POSIX) — target может остаться старым или исчезнуть, при этом tmp-данные были durable. Для state.json (bootstrap state machine) это возврат к устаревшему checkpoint; для secrets.env (0600) — потеря свежих секретов при формально «успешной» записи.
- **Evidence:** fsync только `fh.fileno()` (atomic_writer.py:111); после `commit(...)` (atomic_writer.py:133) нет `os.open(dir, O_RDONLY)`+fsync — контракт crash-safe заявлен шире реализации. · **Impact:** низкая вероятность, но инвариант задокументирован как гарантия; state machine и secrets — критичные потребители. · **Minimal fix:** после replace — fsync dirfd target.parent (одна строка, опция `fsync_dir: bool = True`). · **Required test:** unit с replace_fn-шпионом → assert вызван dir-fsync. · **Phase:** W2

## DATA-104: node.yaml read-modify-write без блокировки — потеря обновлений между процессами
- **Severity:** MED · **Confidence:** HIGH
- **Files:** core/internal/shared/node_yaml/_core.py:352,365 · **Symbols:** `_write_back` (через `atomic_write_text`) · **Invariant:** конкурентные RMW node.yaml сериализуются (регистрация проекта не теряется)
- **Violating scenario:** START: node.yaml без проекта X. Операция: процесс A (`project_registry.register` — scaffold) и процесс B (node-update φ10 `node_config_update`) одновременно читают node.yaml, каждый рендерит свою версию. Сбой: нет — обычная гонка. END: last-writer-wins — регистрация X из A затёрта B; проект существует на диске, но отсутствует в реестре → reconciler/converge/vhost_renderer его не видят. file_lock.py используется только orchestrator/deploy_history/state_store (file_lock.py:14-16) — node_yaml в списке нет.
- **Evidence:** `_core.py:352` — атомарна запись, не транзакция RMW; shared/AGENTS.md подтверждает: потребители FileLock — 3 модуля, node_yaml отсутствует. · **Impact:** рассинхрон реестра; восстановление ручное (повторный register). · **Minimal fix:** flock `{node.yaml}.lock` вокруг read+write_back (переиспользование FileLock, timeout=30). · **Required test:** два процесса RMW параллельно → assert обе правки присутствуют. · **Phase:** W2

## DATA-105: Прямые неатомарные write_text в живые конфиги/состояния ноды (6 сайтов, читатели — внешние процессы)
- **Severity:** MED · **Confidence:** HIGH
- **Files:** core/internal/monitoring/prometheus_targets.py:87 · core/internal/scaffold/vhost_renderer.py:650 · core/internal/scaffold/gen_env_platform.py:501 · core/internal/bootstrap/docker_installer.py:172 · core/internal/bootstrap/converge/projects.py:300 · core/internal/bootstrap/lifecycle/htpasswd.py:148 · **Symbols:** `generate_prometheus_target`, vhost render, `gen_env_platform` main, daemon.json writer, stub env writer, htpasswd writer · **Invariant:** конфиг, читаемый внешним процессом, никогда не наблюдается в частично записанном виде
- **Violating scenario (общий):** START: валидный файл. Операция: `Path.write_text` (truncate → полная запись). Сбой: прерывание посреди записи ИЛИ читатель обращается в момент окна (truncate-then-write — окно всегда есть даже без сбоя). END по читателям: Prometheus file_sd — parse error, дроп всех target'ов проекта до следующего render; nginx reload на частичном vhost — config test FAIL; dockerd restart на усечённом daemon.json — Docker не стартует (bootstrap-фаза); усечённый htpasswd — basic-auth status-page ломается.
- **Evidence:** все 6 сайтов — plain write_text, atomic_writer не импортирован (grep-срез write_text, core/internal, 80 матчей); канон (atomic_writer.py:9-14) перечисляет мигрированных потребителей — эти 6 вне списка без задокументированного исключения (в отличие от json_writer.py TRAP[DOCKER-BIND-MOUNT]). · **Impact:** от дропа метрик до неработающего Docker на ноде. · **Minimal fix:** миграция на atomic_write_text (для daemon.json/htpasswd — с mode 0600/0644 по текущему chmod); для prometheus-target — проверить отсутствие bind-mount-инода (dir scan, не single file — безопасно). · **Required test:** для каждого сайта — fault-write → assert старый файл цел. · **Phase:** W2-W3

## DATA-106: practices GENERATED-набор — транзакции нет, но маркер консистентности (practices.lock sha256) есть; усечение lock безопасно-фейлится
- **Severity:** LOW · **Confidence:** MED
- **Files:** core/internal/practices/generators.py:601-621,497-544 · **Symbols:** `write_generated_file`, `render_lock`, `read_lock` · **Invariant:** набор {pyproject, pre-commit, conftest, test_health, practices.lock} согласован или обнаруживаемо рассогласован
- **Violating scenario:** crash между записями файлов → файлы новые, lock старый → sha-мismatch в `files:` → детект K1/K3 ([PRACTICES:DRIFT]). Crash во время записи самого lock → усечённый YAML → `read_lock` возвращает None → проект трактуется unmanaged → L1-блок деплоя ([PRACTICES:UNMANAGED]). Оба END-состояния fail-safe (блокируют, не молча пропускают) — в отличие от DATA-101/102. Остаточный риск: окно между файлами и lock при активном K3 на VPS — старый lock + новые файлы доставлены payload'ом вместе (receive, DATA-101) — рассинхрон внутри одного payload-набора наследует DATA-101.
- **Evidence:** generators.py:507 «files: path → sha256(rendered content)»; read_lock None → unmanaged (generators.py:551-552). · **Impact:** минимальный — деградация в visible-блок. · **Minimal fix:** не требуется сверх DATA-101 (fix payload-транзакции закрывает и это окно). · **Required test:** — (покрыт K1 drift-тестами). · **Phase:** W3 (верификация после DATA-101)
