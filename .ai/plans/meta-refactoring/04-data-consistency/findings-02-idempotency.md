## DATA-201: Postgres-хук: роль существует + credentials утрачены → тупик (GRANT/creds/env-regen не выполняются никогда)
- **Severity:** HIGH · **Confidence:** HIGH
- **Files:** core/modules/postgres/hooks/on_project_deploy.py · **Symbols:** `ensure_project_db_access` (ранний return L237–248), `_read_credentials` (L327), GRANTs L263–266, regen-gate L274–276 (`if created:`) · **Invariant:** повторный деплой проекта восстанавливает шаред-доступ (роль/GRANT/credentials/.env.platform) — хук идемпотентен и сходится к desired state.
- **Violating scenario:** START: deploy#1 создал роль `app_user` + `.platform-db.env` (0600, вне payload whitelist — строка 365 «вне payload»). Проектный каталог утрачен/пересоздан (remove-project → new-project, DR-перенос): `.platform-db.env` НЕ доставляется payload'ом. Операция: deploy#2 → `ensure_project_db_access`: `role_exists=True`, `_read_credentials()={}` → warning «credentials NOT refreshed» → **return 0** (L248). Повтор/сбой: каждый следующий деплой проходит ту же ветку. END: GRANT CONNECT/CREATE/USAGE не выполнены, `.platform-db.env` не переписан, `.env.platform` не регенерирован — пароль роли неизвестен платформе навсегда, проект не может подключиться к СВОЕЙ БД; автосходождения нет (пароль принципиально не ротируется — инвариант «password unchanged»).
- **Evidence:** `"Role '%s' exists but password unknown (no %s) — credentials NOT refreshed"` → `return 0` (L243–248); GRANT-блок стоит ПОСЛЕ раннего return (L263–266); regen только `if created:` (L275).
- **Impact:** потеря доступа проекта к БД после любой утраты `.platform-db.env`; единственное лечение — ручной `ALTER ROLE ... PASSWORD` оператором. Дополнительно: одноразовый флаг `created` делает regen невоспроизводимым — если первая регенерация упала (non-fatal WARN), последующие деплои её никогда не повторят.
- **Minimal fix:** при role_exists+no-creds не выходить рано: выполнить идемпотентные GRANTs, сгенерировать новый пароль через `ALTER ROLE ... PASSWORD` (ротация безопасна — creds-файла нет, ломать нечему), записать `.platform-db.env`, вызвать regen; regen-гейт — «пароль инжектирован?», а не флаг created.
- **Required test:** unit: роль существует, creds-файл отсутствует → после вызова GRANT выдан, `.platform-db.env` создан, пароль валиден (CONNECT-проба). Negative: частичное создание «роль есть, БД нет» → CREATE DATABASE + GRANT выполняются.
- **Phase:** W2 (DevPlan 133) / repair K1

## DATA-202: LiteLLM provisioning: transient-сбой lookup неотличим от «ключа нет» → duplicate key rows; httpx-исключения не ловятся → обрыв цикла
- **Severity:** HIGH · **Confidence:** HIGH
- **Files:** core/internal/llm/admin_client.py, core/internal/llm/key_provisioner.py · **Symbols:** `get_key_by_metadata` (except → None, admin_client L421–427), `provision_all` (lookup L589, GENERATE ветка L634–656, except `(OSError, ConnectionError, TimeoutError)` L626/L657) · **Invariant:** «IDEMPOTENT: repeated calls produce identical keys» (key_provisioner @invariants) — один ключ metadata.project=X на потребителя.
- **Violating scenario:** START: у проекта X есть виртуальный ключ K1 в LiteLLM DB. Операция: `make provision-llm` (φ11 llm-keys) в момент недоступности litellm (рестарт контейнера той же фазы). `get_key_by_metadata` ловит ConnectError/Timeout/non-404 HTTPStatusError и возвращает **None** — та же семантика, что «404 нет ключа». Повтор/сбой: provision_all уходит в GENERATE → создаётся K2 c тем же metadata.project=X (LiteLLM не дедуплицирует metadata). END: две активные key-строки на один проект; `get_key_by_metadata` вернёт «первый попавшийся» (admin_client L361–363), persist-стор перезапишется произвольным из них → mapping key→project рассинхронизирован: в `.env`/store может попасть токен, не равный реально используемому проектом; бюджеты split между K1/K2, старый K1 остаётся активным.
- **Evidence:** `except (httpx.HTTPError, httpx.ConnectError, httpx.TimeoutException) ... return None` (admin_client.py:421–427); `existing_key = client.get_key_by_metadata(project=consumer_name)` → falsy → «GENERATE '%s': no existing key found» (key_provisioner.py:589,635–656). Агравирующий фактор: except-clause L626/657 `(OSError, ConnectionError, TimeoutError)` НЕ перехватывает httpx-иерархию (httpx.HTTPError ⊄ OSError/builtin ConnectionError) — комментарий «falling through to generate» недостижим, реальное поведение generate/update-fail = вылет из provision_all mid-loop (частичный провижининг остальных потребителей до generic-except main).
- **Impact:** дубли ключей (расход бюджета, stale models, невозможность отзыва «правильного» ключа автоматически), тихий рассинхрон key→project; обрыв цикла оставляет часть потребителей без ключей.
- **Minimal fix:** различать «нет ключа» от «транспортный сбой»: get_key_by_metadata возвращает sentinel/raise на connection-error (None только для 404/пустого списка); в provision_all transient → skip-with-WARNING, не GENERATE. Except-клаузы дополнить `httpx.HTTPError`.
- **Required test:** fake-client: первый lookup → ConnectError → assert generate_key НЕ вызван, WARNING записан; negative: lookup 404 → generate ровно 1 ключ; повторный provision → IDEMPOTENT SKIP.
- **Phase:** φ11 llm-keys / DevPlan 049 P4

## DATA-203: Bootstrap false idempotency: φ1 (firewall/tor) и φ7 (certificates) вне hash-инвалидации — done-SKIP при изменившихся входах
- **Severity:** MEDIUM · **Confidence:** HIGH
- **Files:** core/internal/bootstrap/lifecycle/state_machine.py (L262–271 `_HASH_INVALIDATED_PHASES`), core/internal/bootstrap/lifecycle/cli.py (L773–807 skip), core/internal/bootstrap/lifecycle/phases/docker.py (L506 TOR-gate), core/internal/bootstrap/firewall.sh (thin facade, args из env/φ1) · **Symbols:** `phase_needs_rerun`, `_phase_input_hash`, `_run_phases` · **Invariant:** bootstrap-node строго идемпотентен = повторный запуск приводит ноду к желаемому состоянию, а не маскирует дрейф.
- **Violating scenario:** START: нода забутстраплена, φ1=done, φ7=done в state.json. Операция: (a) renewal-cron acme.sh молча сломался → wildcard-сертификат истёк; оператор запускает `make bootstrap-node NODE=<n>` ожидая реконсиляцию; либо (b) TOR_ENABLED/node-firewall входы изменились (node-configs перевыданы). Повтор/сбой: cli: `status == "done"` → `phase_needs_rerun("system_bootstrap"/"certificates")` → False (фазы вне frozenset) → «already done — skipping». END: (a) nginx продолжает отдавать истёкший сертификат — ssl_provision не запускается ни в init-режиме, ни в update-режиме ноды без Tor (единственный re-apply firewall/ssl в update — `_registry_step_firewall` гейтится `TOR_ENABLED != true → skip`, docker.py:506–508; ssl закрывается только φ12); (b) ufw-baseline/tor-privoxy правило не перевыполняется — ложное «повтор = no-op» фиксирует дрейф.
- **Evidence:** `# Фазы, инвалидируемые content-hash'ом... Прочие фазы (φ1-φ7, φ9-φ10)... их done не сбрасывается hash'ом` + frozenset {DEPLOY_SERVICES, CONVERGE_SERVICES, REGISTRY_UPDATE, DEPLOY_UPDATE, CONVERGE_UPDATE} (state_machine.py:262–271); `logger.info(... "Phase %s already done — skipping") → continue` (cli.py:795–796, 806–807).
- **Impact:** «идемпотентный bootstrap» превращается в «первый прогон выиграл»: сертификат/firewall/tor-канал чинятся только обходными путями (ручной rm state.json / --force / node-update при Tor). Некорректно как гарантия канона (инвариант 6 root).
- **Minimal fix:** включить certificates и system_bootstrap в `_HASH_INVALIDATED_PHASES`; для φ7 добавить в hash входы доменов node.yaml + mtime/acme-home состояния; для φ1 — TOR_ENABLED + firewall-аргументы. Либо внутри done-SKIP делать лёгкую freshness-проверку (cert expiry threshold, ufw status verify) перед continue.
- **Required test:** state.json с φ7=done + истёкший cert (fake facts path_isfile/expiry) → phase_needs_rerun(certificates)=True; φ1=done + TOR_ENABLED flip false→true → re-run.
- **Phase:** B9 state machine (T9.3 расширение)

## DATA-204: acme-cron guard вакуумный: маркер «s3_ssl_cache» никогда не появляется в crontab — fast-path мёртв, migrate реинсталлит при каждом прогоне
- **Severity:** LOW · **Confidence:** MEDIUM
- **Files:** core/internal/bootstrap/cron_installer.py · **Symbols:** `install_acme_cron` (guard L67–72), `migrate_acme_cron_if_needed` (grep L131–137) · **Invariant:** «Idempotent: crontab entry already carrying s3_ssl_cache → no-op» (MODULE_CONTRACT cron_installer).
- **Violating scenario:** START: cron установлен. Операция: повторный bootstrap/update → cert_orchestrator вызывает install/migrate. Повтор/сбой: renew-hook регистрируется отдельной командой `acme.sh --renew-hook 'python3 .../s3_ssl_cache.py upload ...'` (cron_installer L83–89) — hook персистится acme.sh в account.conf/<domain>.conf, а cron-строка от `--install-cronjob` содержит только `acme.sh --cron --home ...`. Guard `if "s3_ssl_cache" in result.stdout` (L70) и migrate-детект «old entry» (L137) НИКОГДА не совпадают → каждая проверка считает cron «старым». END: full `--install-cronjob` + re-register hook при каждом прогоне; отсутствие дублей держится ТОЛЬКО на внутренней дедупликации acme.sh (он сам вычищает свои строки) — контракт «no-op if present» не выполняется кодом этого модуля.
- **Evidence:** guard `if result.returncode == 0 and "s3_ssl_cache" in result.stdout: ... return True` (L70–72) против установки hook вне crontab (L83–84 `[acme_sh, "--renew-hook", f"python3 '{s3_cache_py}' upload \"$Le_Domain\""]`).
- **Impact:** функционально пока безвредно (acme.sh идемпотентен), но заявленный no-op путь — мёртвый код; любая смена поведения acme.sh (например, append вместо replace) даст реальные дубли cron-запусков незаметно.
- **Minimal fix:** детектить hook по факту: `crontab -l` + grep base-name s3_ssl_cache ИЛИ проверять Le_RenewHook в account.conf; миграционный grep строить по наличию `--renew-hook.*s3_ssl_cache` в conf, а не в crontab.
- **Required test:** integration-фейк crontab с реальной acme-строкой (без маркера) + установленный hook в conf → install_acme_cron = no-op (0 подпроцессов --install-cronjob).
- **Phase:** DRIFT-C4 follow-up (117 G T58.4)

## DATA-205: GRANT-результат в postgres-хуке игнорируется; безусловный IMP:9 «GRANTs ensured» при возможном psql-failure
- **Severity:** MEDIUM · **Confidence:** HIGH
- **Files:** core/modules/postgres/hooks/on_project_deploy.py · **Symbols:** `ensure_project_db_access` L263–266, `_psql` (None на exec-failure, L294–314) · **Invariant:** ALL errors visible (конституция) / non-fatal ≠ silent-success; лог IMP:9 отражает фактический результат.
- **Violating scenario:** START: postgres-контейнер в φ8 только что пересоздан (healthcheck ещё settling). Операция: деплой проекта → хук: роль создана, credentials записаны. Повтор/сбой: оба `_psql(GRANT ...)` возвращают None (exec timeout/OSError) — результат отброшен. END: в логе IMP:9 «GRANTs ensured: CONNECT ON db + CREATE,USAGE ON SCHEMA public → role» при нулевых выданных грантах; проект с валидным паролем получает permission denied на CREATE TABLE — ошибка всплывает в миграциях приложения с несоответствующим симптомом. Следующий деплой самозалечивает (role_exists+creds есть → GRANT снова), но диагностика первого инцидента ведёт не туда.
- **Evidence:** `_psql("-c", f'GRANT CONNECT ON DATABASE "{db_name}" TO "{role}"', runner=runner)` — возвращаемое значение не присваивается (L264–265); следом безусловный `logger.info("[IMP:9][db] GRANTs ensured: ...")` (L266).
- **Impact:** тихая потеря грантов + вводящий в заблуждение success-лог; ломает LDD-контракт (IMP:9 = business assertion, здесь ложная).
- **Minimal fix:** проверять `_psql`-результат каждого GRANT: None/ERROR → IMP:9 CRITICAL-строка + счётчик failed-grants в итоговый лог (non-fatal семантику сохранить); «ensured» печатать только при обоих успехах.
- **Required test:** FakeCommandRunner со scripted rc!=0 на GRANT → лог содержит CRITICAL, «ensured» отсутствует; happy-path → «ensured» присутствует.
- **Phase:** W2 (DevPlan 133) — вместе с DATA-201
