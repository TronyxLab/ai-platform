## DATA-501: Прерывание между CREATE ROLE и записью .platform-db.env необратимо теряет пароль роли
- **Severity:** HIGH · **Confidence:** HIGH
- **Files:** core/modules/postgres/hooks/on_project_deploy.py · **Symbols:** `ensure_project_db_access` (:210-279), `_write_credentials` (:361-379), `_read_credentials` (:327) · **Invariant:** credentials роли `${project}_user` восстановимы; повторный деплой самовосстанавливает доступ
- **Violating scenario:** START: роли нет. Операция: деплой → генерируется `secrets.token_urlsafe(24)` (:250), `CREATE ROLE ... PASSWORD` (:252), далее GRANT (:264-265); сбой `_write_credentials` (OSError/disk full/kill процесса между :252 и :269) — ветка non-fatal, return 0 (:270-271). END: роль существует с паролем, которого нет нигде. Повторный деплой: `role_exists=True` (:237) → creds-файла нет → warning «password unknown — credentials NOT refreshed» и return 0 (:242-248): код принципиально отказывается пересоздавать пароль. Деплой при этом зелёный.
- **Evidence:** :238 «SKIP creation (password unchanged)»; :244-248 early-return; инвариант хука «Non-fatal» (:12) гарантирует, что deploys не блокируются · **Impact:** scram-auth через pgbouncer невозможен, проект без БД; recovery — только ручной `ALTER ROLE`. Аналогичное окно между CREATE DATABASE и ролью оставляет БД без доступа (тоже non-fatal).
- **Minimal fix:** при `role_exists` и отсутствии creds — `ALTER ROLE ... PASSWORD '<new>'` + запись creds (восстановление), либо писать creds ДО CREATE ROLE · **Required test:** unit: role exists + нет .platform-db.env → assert password reset или FATAL, не silent return 0 · **Phase:** P1

## DATA-502: Upload-failure бэкапа не имеет retry между ночами; дамп удаляется из spool без off-site копии
- **Severity:** HIGH · **Confidence:** HIGH
- **Files:** core/modules/backup-cron/scripts/{backup_postgres.py,upload.py,backup-cleanup.sh,entrypoint.py} · **Symbols:** `run_backup` upload-ветка (backup_postgres.py:298-320), `_MAX_RETRIES/_RETRY_INTERVAL_SEC` (upload.py:110-118), `RETENTION_DAYS=7` (backup-cleanup.sh:20,35), cron-only entrypoint (entrypoint.py:63) · **Invariant:** RPO 24ч — nightly дамп достигает S3; spool-fallback = «retry без потери данных»
- **Violating scenario:** START: ночь N, S3 недоступен >90 мин. Операция: 3×30мин retries исчерпаны → WARNING + exit 0 (C1, backup_postgres.py:303-320); дамп остаётся в spool. Cron ставит только 03:00 dump и hourly wal_sync — задачи re-upload несуществующих дампов нет (entrypoint.py). Cleanup (04:00 UTC) удаляет ВСЕ spool-файлы старше 7 дней, не различая uploaded/not-uploaded (нет маркера). END: до 7 суток off-site копии нет вообще; потеря ноды в этом окне = потеря всех данных периода, молча.
- **Evidence:** TRAP[DECISION] C1 «for manual retry» — автоматизма нет; backup-cleanup.sh:31-35 `find -mtime +7 | rm`; retention.py ротирует ТОЛЬКО S3-сторону · **Impact:** тихое нарушение RPO 24ч; единственный сигнал — одна IMP:9 строка лога · **Minimal fix:** маркер `.uploaded` / очередь failed-uploads + шаг re-upload в начале ночного job'а; cleanup удаляет только подтверждённо загруженные · **Required test:** fake-runner: upload rc≠0 → следующий прогон переupload'ит старый дамп; cleanup его пропускает · **Phase:** P1

## DATA-503: pg_dumpall уходит в S3 без шифрования (до или после upload)
- **Severity:** HIGH · **Confidence:** HIGH (код), вне репо возможен провайдерский SSE — кодом не гарантирован
- **Files:** core/modules/backup-cron/scripts/upload.py, backup_postgres.py · **Symbols:** `upload_file` ExtraArgs (:281-293 — только Metadata.sha256), `create_s3_client` (:191-225 — без SSE-параметров), ключ `postgres/pgdumpall_*.sql.gz` (backup_postgres.py:309) · **Invariant:** «шифрование до выгрузки» — канон DR-секции для мастер-ключа (core/AGENTS.md §DR); дампы содержат ВСЕ БД проектов + БД litellm (виртуальные ключи, хэши)
- **Violating scenario:** START: ночной дамп готов. Операция: gzip → upload_file plaintext-объекта в Timeweb S3 (ни age/gpg/openssl в пайплайне — glob scripts/*: только python/sh без крипто; ни ServerSideEncryption в ExtraArgs, ни клиентского шифрования). END: полный логический дамп кластера лежит в объектном хранилище в открытом виде; компрометация S3-ключа (S3_ACCESS_KEY/S3_SECRET_KEY — тот же секретный контур, что и прочие env) = утечка всех данных всех проектов.
- **Evidence:** upload.py:283 `extra_args = {"Metadata": {"sha256": sha256}}` — единственный ExtraArgs; grep age|gpg|encrypt в backup-cron/scripts — 0 · **Impact:** нарушение собственного канона «plaintext за пределы ноды не выходит»; compliance-риск · **Minimal fix:** `age -r <recipient>` (или gpg) дампa перед upload; расширить verify на .gz.age · **Required test:** unit: upload-ключ заканчивается на `.enc`/`.age`, plaintext не покидает spool · **Phase:** P1

## DATA-504: Restore — psql в работающий стек без ON_ERROR_STOP и без pre-restore snapshot
- **Severity:** HIGH · **Confidence:** HIGH
- **Files:** core/modules/postgres/Makefile:49-64 · **Symbols:** таргет `restore` · **Invariant:** канон (AGENTS.md §Безопасность данных): «страховка — pre-restore снэпшот в restore-таргете»; restore атомарен
- **Violating scenario:** START: живой стек (postgres + pgbouncer + проекты + litellm пишут). Операция: `make restore DUMP_FILE=nightly.sql.gz` → `gunzip -c | docker exec -i psql` (:59-63): клиенты не остановлены, pre-restore snapshot НЕ создаётся, `ON_ERROR_STOP` не установлен. Дамп pg_dumpall без `--clean` не DROP'ает существующие объекты → каждый CREATE на живой схеме даёт ERROR, psql молча продолжает. END: Makefile печатает «Restore complete» c exit 0 (exit pipeline = статус docker exec; psql без ON_ERROR_STOP возвращает 0 при SQL-ошибках) — частичная смесь старых/новых данных, тиражируемая как успех.
- **Evidence:** :60/:62 — единственные команды restore; отсутствие snapshot/stop/ON_ERROR_STOP в рецепте; противоречие канонному утверждению о pre-restore снэпшоте · **Impact:** DR-процедура при реальном инциденте даёт неконсистентный кластер при «успешном» restore; RTO-канон невоспроизводим · **Minimal fix:** `psql -v ON_ERROR_STOP=1`; шаг pre-restore pg_dumpall-snapshot; PAUSE pgbouncer / stop стека на время restore · **Required test:** e2e restore-drill на test-VPS: restore поверх непустого кластера → rc≠0 или верифицированная целостность (сейчас requires_node-теста restore нет) · **Phase:** P1

## DATA-505: Общий Redis без аутентификации и префикс-политики — cross-project interference не ограничен технически
- **Severity:** MEDIUM · **Confidence:** MEDIUM
- **Files:** core/modules/redis/docker-compose.base.yml:60-66 · **Symbols:** `command: redis-server --save "" --appendonly no --maxmemory 256mb --maxmemory-policy allkeys-lfu` · **Invariant:** изоляция проектов (БД — строгая роль/GRANT; redis — декларативно «общий кэш», эквивалента ACL нет)
- **Violating scenario:** START: N проектов на shared-cache-net, лимит 256mb. Операция: (a) баг/злонамеренный код ЛЮБОГО проектного контейнера сети выполняет FLUSHALL — команда разрешена всем (нет requirepass/ACL в command, портов нет, но сеть общая); (b) шумный проект заполняет 256mb — allkeys-lfu вытесняет ключи других проектов. END: кэш всех проектов одномоментно пуст/вытеснен. Persistence отсутствует by design (owner verdict wave-redis: cache-only) — рестарт redis = штатная холодная кэш-прогревка, потери данных нет, пока redis используется только как кэш; но контракт «queue/critical state → noeviction elsewhere» ничем не enforce-ится.
- **Evidence:** compose:60-66 (нет ACL/pass); grep FLUSHDB|FLUSHALL по репо — 0 (риск только из проектного кода); grep prefix-конвенции в core/ — ключи `PLATFORM_REDIS_URL` генерируются без namespace-гайда · **Impact:** каскадные cache-miss'ы по всем проектам; при появлении очередей в общем redis — потеря задач · **Minimal fix:** Redis ACL per-project user с key-pattern `<project>:*` + префикс-контракт в шаблонах/gen_env_platform · **Required test:** contract-тест шаблона: пример проекта использует префикс; integration: ACL запрещает чужой префикс · **Phase:** P2

- **Files:** core/modules/litellm/docker-compose.base.yml:63-67,131-135; docker-compose.test.yml:30-40 · **Symbols:** `command: --config ...` (миграция выполняет entrypoint образа до старта API — evidenced by «verified Prisma migrate 45-55s» в healthcheck-комментариях), `DATABASE_URL: ...@pgbouncer:6432/litellm` · **Invariant:** fix-forward (C5): новая схема против старого кода недопустима; миграции под контролем
- **Violating scenario:** START: litellm работает на схеме vN. - **Evidence:** base.yml:132-134 (Prisma migrate — часть старта образа); test.yml:39-40 (DSN через pgbouncer:6432); модуль litellm не объявляет backup/restore (modules/AGENTS.md: только postgres/backup-cron/hermes) · **Impact:** при откате litellm — нерабочий LLM-фасад всех проектов; риск битой миграции на pgbouncer · **Minimal fix:** отдельный one-shot migrate-job с DSN напрямую на postgres:5432, запуск после успешного ночного дампа · **Required test:** e2e: upgrade→rollback litellm на test-VPS, assert API жив на старом образе · **Phase:** P2
