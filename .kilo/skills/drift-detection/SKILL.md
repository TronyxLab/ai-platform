# §SKILL
# SKILL: Drift Detection — Principal Engineer Pattern

  ## Философия

  Ты не ищешь баги. Ты ищешь дрейф.

  **Дрейф** — любое изменение, которое постепенно ухудшает систему. Баг — это событие. Дрейф — это процесс. Баг можно починить коммитом. Дрейф требует архитектурного решения.

  Дрейф — это энтропия системы. В хорошо спроектированной системе дрейф минимизирован: knowledge живёт в одном месте, контракты синхронизированы, конфигурация не расходится.

  ### Принципы

  1. **Один Source of Truth** — каждое знание должно существовать ровно в одном месте. Всё остальное — ссылки или производные.
  2. **Синхронизация по цепочке** — изменение в A должно автоматически или протокольно распространяться в B, C, D. Если цепочка разорвана — это дрейф.
  3. **Правила едины** — локально, CI, Docker, production используют одни и те же правила. Если они различаются — это дрейф.
  4. **Один способ делать одно** — наличие нескольких механизмов для одного и того же (Secrets Manager + .env, healthcheck в compose + healthcheck в коде) — дрейф.
  5. **Не предлагай код** — найди дрейф, задокументируй, остановись. Предложение кода до архитектурного решения создаёт новый дрейф.

  ---

  ## Расширенная суперпозиция обнаружения дрейфа

  Ключевое нововведение этого скилла — **многомерная суперпозиция**. Вместо последовательной проверки одного типа дрейфа за другим, агент одновременно пребывает во всех состояниях обнаружения, что позволяет находить интерференционные паттерны — места, где сходятся несколько типов дрейфа.

  ### Режим S1: Многомерный скан (Dr Dimensional Superposition)

  Агент запускает ВСЕ 12 измерений дрейфа (см. §Drift Checks) одновременно как параллельные вселенные. Drift-ID присваивается в момент обнаружения. Если один файл попадает в >3 измерений — это **коллапс суперпозиции**: сигнал критического дрейфа.

  **Формат:**
  ```
  ⚡ COLLAPSE: {file_path} — {N} drift dimensions converge
  ├─ DRIFT-{ID}: {type} — {one-line}
  ├─ DRIFT-{ID}: {type} — {one-line}
  └─ CRITICAL: convergence indicates systemic degradation
  ```

  ### Режим S2: Перспективная суперпозиция (Perspective Superposition)

  Агент одновременно играет роли:
  - **SRE** — ищет дрейф в надёжности (healthcheck, timeout, retry, circuit breaker)
  - **Security Engineer** — ищет дрейф в безопасности (secrets, network policies, authentication)
  - **QA** — ищет дрейф в тестах (contract vs implementation, coverage gaps)
  - **Tech Writer** — ищет дрейф в документации (README, ADR, inline docs)
  - **Product Owner** — ищет дрейф между требованиями и реализацией
  - **Oncall Engineer** — ищет дрейф, который разбудит ночью

  Если один и тот же дрейф обнаруживается с разных перспектив — confidence повышается.

  **Формат:**
  ```
  🔭 PERSPECTIVE OVERLAP: {finding}
  ├─ SRE:   {evidence from SRE perspective}
  ├─ Security: {evidence from security perspective}
  └─ Confidence: HIGH (convergence across 2+ perspectives)
  ```

  ### Режим S3: Временна́я суперпозиция (Temporal Superposition)

  Агент одновременно рассматривает три состояния системы:
  - **Прошлое** (git log, оригинальный ADR, первый коммит) — что было задумано?
  - **Настоящее** (текущий код) — что есть на самом деле?
  - **Будущее** (ADR, roadmap, TODO, FIXME, открытые PR) — что планируется?

  Дрейф между прошлым и настоящим — **регрессия**. Дрейф между настоящим и будущим — **плановая несинхронизация**.

  **Формат:**
  ```
  ⏳ TEMPORAL DRIFT: {entity}
  ├─ Past (git {hash}): {original intent}
  ├─ Present ({file}:{line}): {current state}
  └─ Drift type: {REGRESSION | PLAN_DESYNC}
  ```

  ### Режим S4: Слоевая суперпозиция (Layer Superposition)

  Агент одновременно проверяет все слои системы на наличие одинаковых правил:

  | Слой | Что проверяется | Типичный дрейф |
  |------|-----------------|----------------|
  | Инфраструктура | Docker, compose, CI, Kubernetes | Разные версии образов |
  | Приложение | Код, модули, функции | Дублированная логика |
  | Данные | Схемы, миграции, фикстуры | Схема БД ≠ модели кода |
  | Конфигурация | .env, config файлы, defaults | Переменная есть в одном месте, нет в другом |
  | Документация | README, ADR, inline docs | README говорит одно, код делает другое |
  | Контракты | API, типы, интерфейсы, тесты | Тесты проверяют то, чего нет в контракте |

  **Формат:**
  ```
  🏗️ LAYER DRIFT: {rule/concept}
  ├─ Infra ({file}):         {value}
  ├─ App ({file}):           {value}
  ├─ Config ({file}):        {value}
  ├─ Docs ({file}):          {value}
  └─ Contracts ({file}):      {value}
  → {M} layers disagree — rule fragmentation
  ```

  ### Режим S5: Разрешающая суперпозиция (Resolution Superposition)

  Агент одновременно сканирует на разных уровнях гранулярности и ищет дрейф, который виден только на одном уровне, но невидим на других:

  | Уровень | Объект | Пример дрейфа |
  |---------|--------|---------------|
  | Системный | Сервисы, архитектура | Сервис объявлен, но не реализован |
  | Модульный | Пакеты, компоненты | Модуль A импортирует B, но B удалён |
  | Файловый | Конкретные файлы | Версия в Dockerfile ≠ compose |
  | Функциональный | Функции, методы | Параметр функции не используется |

  **Формат:**
  ```
  🔬 RESOLUTION DRIFT: {concept}
  ├─ System:   {finding}
  ├─ Module:   {finding}
  ├─ File:     {finding}
  └─ Function: {finding}
  → Drift visible at {level} only — invisible at other resolutions
  ```

  ### Режим S6: Цепочечная суперпозиция (Dependency Chain Superposition)

  Агент проверяет не только прямые пары файлов, но и цепочки зависимостей: если A зависит от B, а B зависит от C, то дрейф в C каскадно распространяется в A через B.

  **Формат:**
  ```
  ⛓️ CHAIN DRIFT: {concept}
  ├─ C ({file}) — source of truth
  ├─ B ({file}) — intermediate (depends on C)
  └─ A ({file}) — consumer (depends on B)
  → Propagation chain: C → B → A ({N} hops)
  → Cascade impact: change in C breaks A through B
  ```

  ### Коллапс суперпозиции

  Когда множественные режимы суперпозиции обнаруживают дрейф в одном и том же элементе системы, происходит **коллапс** — агент выдаёт единый отчёт:

  | Сигнал | Условие коллапса | Действие |
  |--------|------------------|----------|
  | ⚡ COLLAPSE | Файл в >3 drift dimensions | CRITICAL — блокирующий |
  | 🔭 OVERLAP | Дрейф подтверждён с >2 perspectives | HIGH — требует внимания |
  | ⏳ TEMPORAL | Past ≠ Present + Present ≠ Future | MEDIUM — плановая синхронизация |
  | 🏗️ LAYER | >50% слоёв расходятся | HIGH — системный дрейф |
  | 🔬 RESOLUTION | Дрейф виден на системном уровне | CRITICAL — архитектурный |
  | ⛓️ CHAIN | Цепочка >2 hops | HIGH — каскадный риск |

  ## Drift Checks — 12 измерений

  ### DRIFT-1: Дублирование знаний (Knowledge Duplication)

  Найди знание, которое существует в >1 месте:
  - Версии образов (в Dockerfile, compose, CI, README, .env)
  - Healthcheck логика (в compose, в коде, в entrypoint, в документации)
  - NO_PROXY и proxy-списки (в compose, .env, CI, конфигах приложений)
  - Timing-параметры (таймауты, ретраи, интервалы)
  - Port numbers (в compose, .env, коде, документации)
  - Connection strings (в compose, .env, CI variables, документации)

  ### DRIFT-2: Дублирование логики (Logic Duplication)

  Найди логику, которая >20% повторяет другую логику:
  - Почти одинаковые функции в разных модулях
  - Одинаковая бизнес-логика в разных сервисах
  - Одинаковые валидации в разных местах
  - Одинаковые трансформации данных

  ### DRIFT-3: Расхождение документации (Documentation Divergence)

  Найди, где документация говорит одно, а код делает другое:
  - README описывает архитектуру, которой больше нет
  - ADR обещает решение, которое не имплементировано
  - Inline docs утверждают инварианты, которые нарушены
  - API docs описывают endpoint, которого нет

  ### DRIFT-4: Расхождение контрактов (Contract Divergence)

  Найди расхождение между формальными и фактическими контрактами:
  - Типы в интерфейсе не соответствуют реализации
  - Ожидаемые параметры ≠ фактические
  - Возвращаемые значения ≠ документированные
  - function signature ≠ usage во всех местах вызова
  - @invariants в MODULE_CONTRACT нарушены

  ### DRIFT-5: Расхождение тестов (Test Divergence)

  Найди тесты, которые разошлись с реализацией:
  - Тест проверяет поведение, которое изменилось
  - Тест не обновлён после рефакторинга
  - Тест импортирует удалённый модуль
  - Coverage gap: новая логика без тестов
  - LDD traces (IMP:9-10) не соответствуют actual execution path

  ### DRIFT-6: Расхождение Compose (Compose Divergence)

  Найди расхождение между compose-файлами (base, dev, prod, override):
  - Разные образы для одного сервиса
  - Разные переменные окружения (отсутствует в одном, есть в другом)
  - Разные volume mounts
  - Разные networks
  - Разные healthcheck
  - Сервис есть в одном compose, нет в другом

  ### DRIFT-7: Расхождение CI (CI Divergence)

  Найди расхождение между CI и другими конфигами:
  - Действия в CI отличаются от локального запуска (lint, test, build)
  - Переменные окружения в CI отличаются от .env
  - Версии инструментов в CI ≠ локальным
  - CI запускает не те тесты (или не все)
  - CI шаги не соответствуют Makefile/Taskfile

  ### DRIFT-8: Расхождение Healthcheck (Healthcheck Divergence)

  Найди расхождение в healthcheck-логике:
  - Разные endpoint-ы проверяются в compose vs code
  - Разные интервалы/таймауты между средами
  - Healthcheck есть в compose, но не в коде (или наоборот)
  - Healthcheck проверяет то, что не является критическим
  - Graceful shutdown не реализован, хотя healthcheck настроен

  ### DRIFT-9: Расхождение Env (Env Divergence)

  Найди расхождение между переменными окружения:
  - Переменная есть в .env, но не используется в compose
  - Переменная есть в compose, но не определена в .env
  - Переменная есть в CI, но не в .env
  - Дефолтные значения различаются между файлами
  - Имена переменных различаются (DB_HOST vs DATABASE_HOST)

  ### DRIFT-10: Расхождение README (README Divergence)

  Найди расхождение между README и текущим состоянием:
  - Инструкции по запуску устарели
  - Описанные зависимости неактуальны
  - Примеры конфигурации не работают
  - Список maintainers устарел
  - Badges (CI, coverage) указывают на несуществующие pipeline-ы

  ### DRIFT-11: Расхождение ADR (ADR Divergence)

  Найди расхождение между ADR и реализацией:
  - Решение принято, но не имплементировано (ADR implementation gap)
  - Решение имплементировано иначе, чем записано
  - ADR описывает ограничения, которые нарушены
  - ADR не обновлён после изменения решения
  - ADR обещает revisit дату, которая прошла

  ### DRIFT-12: Расхождение правил (Rule Divergence)

  Проверь, одинаковые ли правила используются:
  - Локально (pre-commit hooks, lint rules)
  - В CI (GitHub Actions, GitLab CI шаги)
  - В Docker (Containerfile, entrypoint)
  - В production (deployment configs, runtime policies)

  Для КАЖДОГО правила проверь все 4 среды. Если хотя бы одна отличается — это дрейф.

  **Типичные расхождения:**
  - Линтер: локально один набор правил, в CI — другой
  - Форматтер: разная версия или конфиг
  - TypeScript strict mode: включён локально, выключен в CI
  - Security scanner: локально не запускается, в CI — блокирует
  - Test runner: разные флаги (--cov, -x, --ff)

  ## Формат каждой находки

  ```
  ### DRIFT-N: {краткое название}
  **Источник:** {файл:строка} → {файл:строка} (откуда vs куда разошлось)
  **Последствия:** {что произойдёт, если не исправить}
  **Вероятность регрессии:** {HIGH | MEDIUM | LOW} — {почему}
  **Дублированное знание:** {что именно продублировано}
  **Source of Truth:** {что является истинным источником}
  **Режимы суперпозиции:** {S1 | S2 | S3 | S4 | S5 | S6} — {какой режим обнаружил}
  ```

  ### Severity

  - **CRITICAL** — дрейф вызовет production incident (разные версии образов, пропущенный healthcheck)
  - **HIGH** — дрейф приведёт к багам или downtime при следующем деплое
  - **MEDIUM** — дрейф замедлит разработку (устаревшая документация, дублированная логика)
  - **LOW** — косметический дрейф (опечатки, устаревшие badges)

  ## Протокол работы

  ### 1. Scope

  Определи границы проверки. Если scope не указан явно:
  - Используй glob `**/*` для обзора
  - Сфокусируйся на docker-compose файлах, .env, CI конфигах, тестах, ADR, README
  - Если файлов >20 — используй task-агентов с subagent_type="explore" для параллельного аудита (см. post-refactor-recovery skill, Phase 1)

  ### 2. Superposition Scan

  Запусти многомерную суперпозицию:
  1. S1 (многомерный скан) — все 12 измерений
  2. S2 (перспективы) — как минимум SRE + Security
  3. S3 (время) — git log для критических файлов
  4. S4 (слои) — все 6 слоёв для каждого найденного дрейфа
  5. S5 (разрешение) — проверь, виден ли дрейф на системном уровне
  6. S6 (цепочка) — проверь propagation chain для каждого дрейфа

  ### 3. Collapse

  При обнаружении интерференции (>3 измерений или >2 перспектив) — коллапс в CRITICAL находку.

  ### 4. Report

  Выведи отчёт в формате:
  - Сводка: N дрейфов, из них CRITICAL: X, HIGH: Y, MEDIUM: Z
  - Каждый дрейф с полным описанием
  - Collapse-сигналы (если есть)
  - Общая оценка: STABLE | DRIFTING | DEGRADING | CRITICAL

  ### 5. Completion

  **Не предлагай код.** Не пиши fix. Не создавай PR. Только отчёт.

  После отчёта:
  - Если найден CRITICAL дрейф → создай {NN}-VerificationReport.md с `$ARTIFACT_CONTRACT` (NN = max existing NN + 1, см. §ARTIFACT_REGISTRY)
  - Если только MEDIUM/LOW → достаточно текстового отчёта
  - Завершись. Не спрашивай "хочешь ли ты, чтобы я починил?"

  ---

  ## Запрещается

  - Писать код или фиксы (нарушает принцип "не предлагай код")
  - Исправлять найденный дрейф самостоятельно
  - Предлагать "а давай я это починю"
  - Игнорировать дрейф, потому что "он был всегда"
  - Путать дрейф с багом (баг — событие, дрейф — процесс)
  - Проверять только один тип дрейфа (нарушает многомерную суперпозицию)
  - Давать confidence HIGH без коллапса хотя бы 2 режимов суперпозиции

  ## Пример

  ```
  # Drift Detection Report

  ## Сводка
  - Всего дрейфов: 7
  - CRITICAL: 1
  - HIGH: 3
  - MEDIUM: 2
  - LOW: 1
  - Superposition collapses: 1 (CRITICAL)
  - Общая оценка: DEGRADING

  ## CRITICAL

  ### DRIFT-1: Image version mismatch — redis
  **Источник:** docker-compose.yml:12 (redis:7.4) → .github/workflows/test.yml:34 (redis:7.2)
  **Последствия:** CI запускает тесты на redis 7.2, production работает на 7.4. Разное поведение, невоспроизводимые баги.
  **Вероятность регрессии:** HIGH — разная минорная версия, breakage guaranteed
  **Дублированное знание:** версия образа redis
  **Source of Truth:** docker-compose.yml (production-ближайший)
  **Режимы суперпозиции:** S1 (DRIFT-6 + DRIFT-7), S2 (SRE), S4 (Infra), S6 (chain: CI → compose)

  ⚡ COLLAPSE: redis image version
  ├─ DRIFT-6 (Compose Divergence): compose не синхронизирован с CI
  ├─ DRIFT-7 (CI Divergence): CI использует другую версию
  └─ CRITICAL: 4 dimensions converge — systemic config fragmentation

  ## HIGH

  ### DRIFT-2: Healthcheck endpoint расходится
  **Источник:** docker-compose.yml:30 → src/api/health.py:15
  **Последствия:** compose проверяет /health, код отдаёт /status. Healthcheck всегда FAIL.
  **Вероятность регрессии:** MEDIUM — зависит от orchestration restart policy
  ...
  ```
