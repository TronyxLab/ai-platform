# §SKILL
# §SKILL
  # SKILL: Test Suite Auditor

  Аудит всего набора тестов проекта. Цель — поддерживать тестовый набор компактным, быстрым, понятным и устойчивым к изменениям архитектуры.

  ## Философия

  - **Не максимизировать количество тестов.**
  - **Не максимизировать покрытие.**
  - **Максимизировать ценность каждого теста.**

  Каждый существующий тест должен оправдывать своё существование.

  ### Ключевые принципы

  1. **Стоимость владения.** Если тест редко ловит регрессии, но часто ломается при рефакторингах — его полезность отрицательна. Оценивай не только пользу, но и цену сопровождения.

  2. **Оценка на уровне набора, а не теста.** Вопрос не «хорош ли этот тест?», а «если удалить этот тест, станет ли проект заметно менее защищённым?». Это позволяет смелее удалять дублирующие и малополезные проверки.

  ## Двухфазный рабочий процесс

  Скилл загружается ролью **Plan (Architect)**. Plan выполняет Фазу 1 (статический анализ) самостоятельно, затем делегирует Фазу 2 (рантайм-валидацию) роли **QA** через `task` tool.

  ### Что QA уже покрывает — не дублировать

  QA (см. `bundlekit/framework-source/roles/qa.xml`) выполняет следующие проверки **в рамках своей штатной работы** при получении scope с тестовыми файлами. Plan НЕ должен их повторять в Фазе 1:

  **Phase 1 step 5 (Test Quality Checks):**
  - Stub detection: `def test_*` под `@pytest.mark.skip` с пустым телом
  - Grep-style detection: структурные `assert "..." in content/text/source/output/result`
  - Missing test rationale: `## @purpose` не описывает предотвращаемую регрессию
  - Skip-stale detection: `@pytest.mark.skip` со ссылкой на удалённый модуль, или файл не менялся >90 дней

  **Phase 2 step 2 (Test Health Metrics):**
  - Skip rate >15% threshold
  - Slow tests >10s (`--durations=5`)
  - Test count delta vs baseline

  **Phase 2 (LDD &amp; Anti-Illusion):**
  - LDD trace analysis (IMP:7-10)
  - Anti-Illusion Rule enforcement
  - Acceptance criteria verification (Phase 2 step 4)

  **MARKUP &amp; TRAP[TEST]:**
  - Полное определение TRAP[TEST] и проверка его наличия в тестах
  - Семантическая разметка: GREP_SUMMARY, STRUCTURE, region markers, ## @purpose, caplog

  ### Фаза 1 — Статический аудит (роль: Plan)

  Выполняется **без запуска тестов**. Plan читает тестовые файлы, анализирует структуру, находит проблемы.

  #### 1.1 Определение scope

  ```
  glob: tests/**/*.py
  ```

  Исключить: `tests/conftest.py`, `tests/__init__.py`, файлы `test_data/`.

  #### 1.2 Измерения аудита (только уникальные)

  Для каждого тестового файла и каждой тестовой функции проверь:

  **D1 — Дублирование**

  Найди тесты, которые:
  - проверяют одно и то же поведение;
  - отличаются только входными данными без увеличения ценности;
  - появились после рефакторинга, но старые версии остались;
  - проверяют одну и ту же ветку кода.

  Маркеры: одинаковые `## @purpose`, похожие assert-паттерны, идентичные setup-блоки.

  Предложи: объединить, удалить, параметризовать (`@pytest.mark.parametrize`).

  **D2 — Тесты ради тестов**

  Найди тесты, которые:
  - проверяют очевидное (языковые конструкции, константы);
  - повторяют реализацию один-в-один;
  - тестируют геттеры/сеттеры без логики;
  - тестируют сторонние библиотеки;
  - существуют только ради покрытия.

  Объясни, почему они не дают ценности.

  **D3 — Хрупкие тесты**

  Найди тесты, которые:
  - ломаются после небольшого рефакторинга;
  - проверяют внутреннюю реализацию (private-методы, структуру классов);
  - требуют >3 моков;
  - имеют сложную подготовку окружения;
  - содержат хардкод-пути (нарушение Zero Hardcode Rule).

  Маркеры: `unittest.mock.patch`, `MagicMock`, `sys.path.append`, hardcoded paths.
  Grep-паттерны (из QA): `grep -E "unittest\.mock\.patch|MagicMock|mock\.patch"` для моков, `grep -E "sys\.path\.append"` для хардкод-путей, `grep -E "\"(/[^\" ]+)+\.[a-z]+\"` для файловых путей.

  Предложи сделать их более устойчивыми.

  **D4 — Мёртвые тесты**

  Найди тесты, которые семантически мертвы:
  - относятся к удалённому функционалу (импортируют удалённые модули);
  - проверяют несуществующие сценарии;
  - никогда не могут упасть (пустой assert, `assert True`, `assert 1 == 1`);
  - содержат `# TRAP[ARCHIVED]` — функционал удалён, тест не обновлён.

  Маркеры: `# TRAP[ARCHIVED]` рядом, импорты удалённых модулей, пустые assert-ы (не путать со skip-stale — это проверяет QA).

  Предложи удалить.

  **D5 — Избыточность**

  Определи:
  - слишком похожие тесты (разница только в данных);
  - чрезмерную детализацию (10 тестов на одну функцию);
  - множество тестов, проверяющих одно поведение с разных углов.

  Предложи минимальный достаточный набор.

  **D6 — Недостающие проверки**

  Определи:
  - важные пользовательские сценарии без тестов;
  - сложную бизнес-логику без покрытия;
  - интеграции без проверки;
  - критические регрессии, которые не обнаружатся существующими тестами.

  Используй DevPlan.md и Brief.md для сопоставления acceptance criteria с тестами.

  Предлагай только действительно важные тесты.

  **D10 — Архитектура тестов**

  Проверь:
  - структуру каталогов (все тесты в `tests/`, нет разбросанных по проекту);
  - именование: `test_&lt;module&gt;.py`, функции `test_&lt;сценарий&gt;`;
  - повторяющийся код (кандидаты в `conftest.py` фикстуры или helpers);
  - фикстуры: используются ли `tmp_path` вместо хардкод-путей;
  - `_write_file` helper дублируется между файлами — вынести в conftest;
  - Anti-Loop протокол: корректность `conftest.py`, сброс счётчика только при 100% PASS.

  #### 1.3 Формат вывода Фазы 1

  ```
  ## Фаза 1 — Статический аудит тестового набора

  ### Общая оценка
  - Файлов: N
  - Тестовых функций: M
  - Общее качество: [Здоровый | Удовлетворительный | Технический долг | Критический]
  - Основные проблемы: ...

  ### D1 — Дублирование
  | Файл:строка | Тест | Проблема | Рекомендация |
  |-------------|------|----------|--------------|
  | tests/test_x.py:42 | test_foo_a | Дублирует test_foo_b | Удалить, оставить test_foo_b |

  ... (аналогично для D2-D6, D10)

  ### Сводка рекомендаций
  - Удалить: N тестов
  - Объединить: N групп
  - Переписать: N тестов
  - Добавить: N тестов
  ```

  ### Фаза 2 — Рантайм-валидация (делегирование QA)

  Plan делегирует запуск тестов, LDD-анализ, проверку производительности и acceptance criteria роли **QA**. QA выполняет эти проверки в рамках своей штатной работы (Phase 1 step 5 + Phase 2 steps 1-4).

  #### 2.1 Делегирование

  ```
  task(
    subagent_type="QA",
    description="Test suite runtime audit (Phase 2 of Test Suite Auditor)",
    prompt="Scope: {список тестовых файлов}. Run Phase 1 step 5 + Phase 2: pytest, skip-rate, slow tests, LDD traces, Anti-Illusion, acceptance criteria."
  )
  ```

  Prompt для QA должен содержать:
   1. Путь к authoritative DevPlan (highest-NN `*-DevPlan*.md` в task folder, см. §ARTIFACT_REGISTRY R1)
  2. Список тестовых файлов (scope из Фазы 1)
   3. Ссылку на VerificationReport.md, если Phase 1 обнаружила проблемы

  QA возвращает свой стандартный Verification Report. Plan использует его для итогового аудит-отчёта.

  ## Итоговый отчёт (роль: Plan)

  Plan объединяет результаты Фазы 1 и ответ QA в единый аудит-отчёт:

  ```
  # Test Suite Audit Report — {дата}

  ## Общая оценка
  - Тестов: N
  - Статическое качество: {оценка}
  - Рантайм: {PASS/FAIL}
  - Уровень техдолга: [Низкий | Средний | Высокий | Критический]

  ## План улучшения

  ### Высокий приоритет (макс. эффект / мин. усилия)
  - [D1] Удалить N дублирующих тестов: ...
  - [D4] Удалить N мёртвых тестов: ...

  ### Средний приоритет (желательные улучшения)
  - [D3] Переписать N хрупких тестов: ...
  - [D5] Объединить N избыточных тестов: ...
  - [D6] Добавить N недостающих тестов: ...

  ### Низкий приоритет (косметика)
  - [D10] Реорганизовать фикстуры: ...

  ## Итог
  Оценка набора тестов по принципу:
  > «Минимальное количество тестов, обеспечивающее максимальную уверенность в корректности системы.»

  - Можно удалить без потери надёжности: N тестов (список)
  - Требуют срочного внимания: N проблем (список)
  ```

  ---

  ## Запрещается

  - Увеличивать покрытие ради процента
  - Писать тесты ради тестов
  - Тестировать сторонние библиотеки
  - Тестировать очевидное поведение языка
  - Дублировать существующие проверки
  - Сохранять тесты только потому, что они уже существуют
  - Рекомендовать удаление тестов без объяснения, почему набор не станет менее защищённым

  ## Предпочтения

  - Меньше тестов → больше ценности каждого
  - Меньше поддержки → выше устойчивость к рефакторингу
  - Меньше времени выполнения → быстрее CI
  - Проверка поведения, а не реализации
